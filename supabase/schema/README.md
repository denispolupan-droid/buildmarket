# Знімки схеми прода

`baseline-YYYY-MM-DD.sql` — повний `pg_dump --schema-only` схеми `public` продової бази
(роль `backup_reader`, без власників і привілеїв). Це **точка відліку**: файли в
`supabase/migrations/` не відтворюють базу з нуля (таблиця `orders` та кілька інших там
не створюються, 14 номерів дубльовані, частина логіки жила лише в БД — див. аудит 03.10.2026).

Правила:
- Знімок не редагують руками. Нову версію кладуть окремим файлом після серії міграцій
  (беруть із артефакту workflow «Nightly full database dump», файл `*.schema.sql`).
- Зміни схеми й далі — тільки через `supabase/migrations/*.sql`, prod → одразу test.
- Щоб підняти базу з нуля: знімок + усі міграції з номером, більшим за дату знімка
  (для 2026-10-03 це 128+).

## Типи БД

`types/database.types.ts` — згенерований `supabase gen types` зі схеми прода (workflow
«Generate DB types», ручний запуск → артефакт → коміт). Руками не редагують; після міграцій
перегенеровують. Підключення `createClient<Database>` до клієнтів у `lib/supabase*.ts` —
окремий крок етапу 1, бо типізований клієнт підсвітить розбіжності в наявних запитах.

## Синк тестової бази

- `test-sync-2026-10-15.sql` — 14 колонок і таблиця, яких бракувало на тесті.
- `test-sync-2026-10-31.sql` — RLS на 23 таблицях і 30 політик: тест був підмножиною
  прода, перевірка схем бачила лише колонки. З 31.10 `schema-parity.yml` порівнює
  колонки, RLS і політики; при розходженні — Telegram.
