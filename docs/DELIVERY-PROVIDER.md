# DeliveryProvider — перевізники за одним контрактом

Аудит 31.10.2026, п. 17. Зроблено 08.11.2026.

## Проблема

Рух посилок синхронізувався трьома копіями гілок в одному файлі (`lib/delivery-sync.ts`,
~600 рядків): Нова Пошта, точки видачі Rozetka, «ROZETKA Доставка» власного договору.
Кожна гілка сама оновлювала колонки замовлення, сама вирішувала, коли «прийнято
перевізником», сама проводила РН при врученні, сама слала сповіщення й сама
записувала витрати продавця. Укрпошта й Meest (з маркетплейсів) довго вважалися
Новою Поштою (інцидент 02.11.2026). Четвертий перевізник означав четверту копію.

## Рішення

`lib/delivery/`:

- `types.ts` — контракт `DeliveryProvider`: `handles(delivery_type)`, пакетний
  `track(orders) → Map<order_id, ParcelUpdate>`, прапорець `notifiesParcelEvents`.
  `ParcelUpdate` описує рух у термінах конвеєра: `statusText`, `phase`
  (`created | in_transit | arrived | delivered | returning | unknown`), `carrierAccepted`,
  `deliveredAt`, `patch` (колонки перевізника), `expenses` (витрати продавця при
  врученні, ключ по ЕН), `onAccepted` (гак провайдера).
- `providers/nova-poshta.ts` — getStatusDocuments пачками по 100, вартість/платник,
  час вручення, зворотна накладна + утримання з дропшип-партнера, підказка Rozetka
  «статус 3» для замовлень маркетплейсу з ЕН НП. Невідомі `delivery_type` — НП
  (історична поведінка, `isNpTracked`).
- `providers/rozetka-points.ts` — статус замовлення в кабінеті як рух посилки; лідер
  об'єднаної посилки («RMP-…» на кілька замовлень); сусіди вручаються разом з лідером.
- `providers/rz-delivery.ts` — трекінг пачкою; комісія за переказ післяплати й
  доставка за наш рахунок як витрати.
- `providers/manual-postal.ts` — Укрпошта/Meest: трекінгу немає, вручення підтверджує
  синк площадки або менеджер.
- `registry.ts` — порядок провайдерів; `providerFor(delivery_type)`.
- `sync.ts` — один конвеєр: текст/колонки → «прийнято» (сповіщення «поїхала», гак) →
  «прибула» (сповіщення) → «вручено» (РН за ЕН, витрати, «Доставлено» з подіями outbox
  покупцю — Telegram + email, як і з картки). Скасовані — лише текст.
  `lib/delivery-sync.ts` лишився тонким входом для крона й кнопки адмінки.

Новий перевізник = один файл у `providers/` + рядок у `registry.ts`. Конвеєр, облік,
сповіщення й outbox не правляться.

## Що НЕ в контракті (свідомо)

Створення накладних і друк лишаються в існуючих роутах (`/ttn` для НП, `/rz-ttn`,
`/rozetka-delivery-ttn`): їхні тіла запитів не мають спільної форми (НП — відділення/
адреса/поштомат/юрособа, RZ — відділення й місця, Rozetka — лише посилання на
кабінет). Спільний крок там один — запис ЕН у замовлення й подія outbox — і він уже
спільний (`replace-ttn`, `ship`). Коли з'явиться перевізник із власним API створення
(Укрпошта/Meest за договором), сюди додається `createTtn()` з мінімальним DTO, а не
копія роуту.

## Перевірка

- Юніт: `tests/delivery-provider.test.ts` — реєстр, НП (фази, витрати, гак Rozetka),
  RZ (витрати), точки Rozetka (лідер/сусіди, вирішене повернення).
- Інтеграційні: `tests/accounting/delivery-smoke.test.ts` (вручення → РН → облік) — без змін.
- У проді після деплою: `delivery-status` крон щогодини; `carrier_status_synced_at`
  і `delivered_at` рухаються; I7 (вручені без РН) зелений.
