# Життєвий цикл замовлення

Актуально на 12.10.2026. Джерело правди для статусів і переходів у коді —
`lib/orders/status.ts`; цей документ пояснює, **чому** так і що відбувається
в обліку на кожному кроці. Якщо документ і код розходяться — правте обидва.

## Статуси

| Статус | Що означає | Хто ставить |
|---|---|---|
| `new` | Замовлення створене (сайт, кабінет дропшипера, імпорт з Prom/Rozetka/Епіцентр, ручне в адмінці) | створення |
| `pending_payment` | Чекає онлайн-оплату (рахунок карткою) | створення / картка |
| `confirmed` | Взяте в роботу; визначено режим виконання (`fulfillment_mode`: supplier / own / mixed); власний товар зарезервовано | `/confirm`, вебхук Monobank (після оплати), картка |
| `awaiting_stock` | Змішане виконання: частина товару замовлена в постачальника (створено закупівлю) | `/confirm` |
| `picking` | Товар надійшов, збираємо | прийом закупівлі (авто), картка |
| `shipped` | Відвантажено: створено **чернетку РН** з номером посилки, борг постачальнику проведено | `/ship` |
| `delivered` | Вручено покупцю: РН **проведена** (виручка, COGS, склад, комісія МП) | синк доставки (НП / Rozetka / RZ), синк Prom, `/ship` для самовивозу, картка («Доставлено») |
| `cancelled` | Скасовано; що сторнується — залежить від того, де зупинилось | картка, сторож скасувань МП |

Порядок для «вперед/назад»: `new = pending_payment < confirmed < awaiting_stock < picking < shipped < delivered`; `cancelled` поза шкалою.

## Переходи

Штатні (система або менеджер у звичайній роботі):

```
new ────────────┬─> confirmed ─┬─> shipped ──> delivered
                │              ├─> picking ─┘
                │              └─> awaiting_stock ─> picking / shipped
pending_payment ┘
будь-який ──> cancelled
delivered ──> cancelled   (= повернення; сторно робить документ, не статус)
```

Ролі:
- **менеджер** — лише вперед; скасувати може тільки `new`;
- **адмін** — будь-куди, але зворотні ходи (`shipped → confirmed`, `cancelled → …`, `delivered → …`) повертаються в відповіді як `warnings`: резерви, чернетки РН і проводки **не перераховуються** автоматично;
- **система** (крони, вебхуки) — лише штатні переходи.

Реальна статистика за липень–жовтень 2026 (`order_status_history`): 585 `new→confirmed`,
569 `confirmed→shipped`, 511 `shipped→delivered`, 97 скасувань, 9 зворотних ходів адміна.

## Запобіжники

- `shipped` / `delivered` руками **без жодної РН** → 409 (`manualStatusWithoutSaleError`).
  Інакше продаж не буде проведено (інцидент #26091195, 03.10.2026).
- `delivered` ставиться лише коли **всі** чернетки РН проведені і є хоча б одна проведена
  (`allOrderSalesPosted`); замовлення без документів лишається `shipped`, адмін отримує
  один алерт і прапорець `sale_doc_missing` у `flags`.
- Самовивіз із накладною перевізника → відгрузка відмовляє (`pickupWithTtnError`).
- `shipped` у борг → кредитний контроль (`checkOrderCredit`) до запису статусу.

## Облік по кроках

| Крок | Документи й проводки |
|---|---|
| `/confirm` | резерв власного товару (`stock_reservations`); для mixed — закупівля (`purchase_order`) |
| `/ship` | РН-чернетка з `tracking_number` (`createSaleDraft`); дропшип-борг постачальнику → `inventory_transit`; збори МП, що списуються при передачі перевізнику (Rozetka Smart, доставка в точку видачі) |
| вручення | `completeShipmentByTtn` → `applyCompletionEffects`: проводиться РН (виручка, COGS, склад, знімається резерв), комісія МП по рядках цієї РН, доставка за наш рахунок, COD партнеру |
| скасування до відгрузки | знімається резерв, повертається баланс партнера |
| скасування після відгрузки | чернетки РН гасяться; борг постачальнику й «товар у дорозі» лишаються до рішення людини (повернення) |
| скасування після вручення | **тільки документом повернення** (`↩ Повернення` в картці); статус сам нічого не сторнує |

Правило: усі гроші проводяться функцією БД `record_money_txn` через `lib/accounting/*`;
прямих записів у `money_entries` у коді немає і не має з'являтися.

## Як міняти статус у коді

Єдиний шлях — `transitionOrder(db, orderId, to, actor, via, extra?)` або, коли статус
пишеться разом з іншими полями тим самим `UPDATE`, `buildStatusPatch(...)`. Обидва:
- ставлять мітку стану (`shipped_at` / `delivered_at` / `cancelled_at`; `confirmed_at`, якщо порожня);
- дописують `status_history` запис `{ status, at, by, via }` — `via` каже, з якого екрана
  чи крона прийшла зміна;
- при тому самому статусі нічого не перезаписують.

Паралельно тригер БД `fn_track_order_status` веде повний журнал `order_status_history`
незалежно від коду — це контрольний слід, навіть якщо хтось напише `status` напряму.
