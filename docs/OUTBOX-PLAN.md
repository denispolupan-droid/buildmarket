# Outbox подій замовлення — дизайн (чернетка для рішення власника)

Аудит 31.10.2026, п. 19: «Outbox-таблиця подій замовлення + Vercel Queues/Workflow
для пушів у МП, уведомлень, синка поставщиків, генерации фидов».
Документ — щоб домовитись про межі, схему й порядок, **перш ніж писати код**.

## 1. Навіщо (проблема, як вона є зараз)

Побічні ефекти після зміни замовлення (пуш статусу/ЕН на площадку, лист чи
Telegram покупцю) зараз запускаються **з обробника запиту «вистрілив і забув»**:
`setPromTTN(...).catch(alertAdmin)`, `setRozetkaOrderStatusChained(...).catch(console.error)`
тощо — 8 місць у `ship`, `confirm`, `orders/[id]` (статус, скасування), `orders` (нове).

Що з цього виходить:

| Симптом | Приклад | Чим лікується сьогодні |
|---|---|---|
| Площадка не відповіла / таймаут | 03.11: Prom 20 с → алерт «ЕН не передана» | крон `prom-orders` раз на 5 хв звіряє й допушує (самолікування є для Prom, Rozetka, Епіцентру) |
| Функція Vercel завершилась раніше, ніж промис | відповідь уже пішла, промис обірвано | ніхто: пуш губиться мовчки, поки крон не помітить розходження |
| Алерт раніше за лікування | власник біжить перевіряти, крон уже допушив | текст алерту (03.11) каже «крон допушить» |
| Уведомлення покупцю (Telegram/email) впало | `console.error('[status email]')` | ніяк — повтору немає |
| Непрозоро, що саме й коли пішло на площадку | дивимось логи Vercel по rid | логи зникають, слід у БД немає |

Самолікування кронами працює для площадок, але воно **непряме** (порівнює стан,
а не знає, що саме не доїхало) і не покриває уведомлення. Outbox робить побічний
ефект **записом у тій самій транзакції**, що й зміна замовлення, а доставку —
окремим кроком із повторами й слідом.

## 2. Що НЕ робимо (межі)

- **Синк постачальників** (`sync-suppliers`, кожні 2 год, 8 000 рядків прайсу) —
  це пакетна робота за розкладом, не подія замовлення. Лишається кроном із
  `withCronLock` + `maxDuration=300`. Черга тут нічого не додає.
- **Генерація фідів** (`prom-feed`, `google-merchant-feed`, `feed`) — проблема
  не в доставці, а в кеші: фід рахується на кожен запит (`Cache-Control: no-store`).
  Правильний інструмент — `revalidate`/`cacheLife` 5–15 хв + інвалідація тегом
  при зміні цін (тег `products` уже є). Окремий маленький пункт, без черг.
- **Алерти адміну** (`alertAdmin`) — лишаються прямими: це канал останньої
  надії, він не має залежати від черги.
- **Імпорт замовлень з площадок** — уже крон + staging (міграція 153); не чіпаємо.
- Workflow SDK (durable steps, sleep, hooks) — не потрібен: у нас немає
  багатокрокових процесів із очікуванням; усе — «одна подія → один виклик API».

## 3. Події (каталог)

| Подія | Коли виникає | Обробники (кожен — свій рядок outbox) |
|---|---|---|
| `order.confirmed` | `confirm` | `mp.push_status` (Prom/Rozetka/Епіцентр за каналом), `customer.notify_status` |
| `order.shipped` | `ship` (і перевідвантаження) | `mp.push_ttn` (+ статус), `customer.notify_status` |
| `order.status_changed` | `orders/[id]` PATCH статусу | `mp.push_status`, `customer.notify_status` |
| `order.cancelled` | `orders/[id]` скасування | `mp.push_status` (скасування на площадці), `customer.notify_status` |
| `order.created` | `orders` (сайт/ручне) | `admin.notify_new_order` (Telegram) |
| `order.ttn_replaced` | `replace-ttn`, видалення + створення ЕН | `mp.push_ttn` |

Обсяг: ~6,4 замовлення/день, ~6,5 відправлень/день, 173 замовлення площадок за
30 днів → **20–40 рядків outbox на день**. Це не про пропускну здатність, а про
гарантію і слід.

## 4. Схема

```sql
create table outbox_events (
  id            bigint generated always as identity primary key,
  aggregate     text not null,              -- 'order'
  aggregate_id  uuid not null,              -- orders.id
  event         text not null,              -- 'order.shipped'
  handler       text not null,              -- 'mp.push_ttn' | 'customer.notify_status' | …
  payload       jsonb not null default '{}',-- знімок потрібних полів (ЕН, статус, канал)
  dedupe_key    text not null unique,       -- '<handler>:<aggregate_id>:<event>:<версія>' — один і той самий намір не дублюється
  status        text not null default 'pending'
                check (status in ('pending','done','failed','skipped')),
  attempts      int  not null default 0,
  next_at       timestamptz not null default now(),   -- коли пробувати далі (backoff)
  locked_until  timestamptz,                -- оренда диспетчера
  last_error    text,
  created_at    timestamptz not null default now(),
  done_at       timestamptz
);
create index on outbox_events (next_at) where status = 'pending';
create index on outbox_events (aggregate_id, created_at desc);
```

- **Запис — у тій самій транзакції, що й зміна замовлення.** Зараз зміна
  статусу йде через `transitionOrder` (один UPDATE через PostgREST) — щоб запис
  outbox був атомарним із ним, `transitionOrder` викликає SQL-функцію
  `order_transition_with_outbox(...)` (plpgsql: UPDATE orders + INSERT outbox).
  Без цього є вікно «статус змінили, outbox не записали» — те саме, що зараз.
- `dedupe_key` замість «повторного пушу»: `ship` → `mp.push_ttn:<order>:<ttn>`;
  друга спроба відвантажити з тією ж ЕН не створить другий рядок.
- `payload` — знімок, а не посилання: обробник не має перечитувати замовлення,
  щоб не пушити вже змінений стан. Але **перед викликом площадки** обробник
  звіряє, що замовлення досі в тому стані (інакше `skipped`).

## 5. Диспетчер

Два шляхи до одного обробника:

1. **Швидкий (опціонально, фаза 2): Vercel Queues** — після коміту транзакції
   `send('outbox', { id })`; push-обробник `app/api/queues/outbox/route.ts` бере
   рядок за id, орендує (`locked_until = now()+5 хв`), виконує, ставить `done`.
   Черга — лише **будильник**: втрата повідомлення нічого не ламає.
2. **Надійний (фаза 1): крон-sweeper** `cron/outbox-sweep` раз на хвилину
   (Pro-план дозволяє `* * * * *`): бере `pending` з `next_at <= now()` і
   `locked_until` у минулому, пачкою до 20, той самий код обробників.

Правила:
- **Ідемпотентність обробника** — обов'язкова: Prom/Rozetka/Епіцентр уже
  толерантні до повторного пушу того самого номера/статусу (перевірено 28.09,
  `PROM_TTN_ALREADY_SET`), Telegram/email — через `dedupe_key` + позначку в
  `notification_log` (нова таблиця не потрібна: `done` в outbox і є слід).
- **Backoff**: 1 хв, 5, 15, 60, 6 год; після 8 спроб → `failed` + `alertAdmin`
  один раз («не доставлено за добу»). Поки йдуть повтори — **без алертів**
  (сьогоднішня історія з Prom більше не турбує власника).
- **Порядок у межах замовлення**: обробники одного `aggregate_id` виконуються
  послідовно за `id` (sweeper бере по одному pending на замовлення). Між
  замовленнями — паралельно, до 5 одночасно (ліміти НП/Prom «To many requests»).
- **Пропуск**: якщо замовлення вже в іншому стані (скасоване після confirmed) —
  `skipped` з причиною, не помилка.
- **Таймаути** — ті самі `fetchWithTimeout`, що в клієнтах; крон з
  `maxDuration=60`.

## 6. Чим це краще за «крон звіряє й допушує»

Крони-самолікування лишаються як **друга лінія** (вони ловлять і те, чого outbox не
знає: зміни з кабінету площадки). Outbox дає: (а) запис побічного ефекту атомарно
зі зміною; (б) явний слід «що, коли, скільки спроб, яка помилка» у картці
замовлення; (в) повтори для уведомлень, яких зараз немає; (г) тишу в Telegram,
поки система сама лікує.

## 8. Вартість

Vercel Queues — бета на всіх планах, облік за операціями (4 KiB = 1 операція;
Hobby: 1 млн включено, Pro — за використанням, регіональні ціни). При 40 подіях
на день це десятки операцій на день — у межах похибки. Supabase: +1 таблиця,
+40 рядків/день, крон раз на хвилину — один легкий SELECT по частковому індексу
(IO-бюджет nano витримує; порівняно з 12 запусками `prom-orders` на годину це
дрібниця).

## 9. Тести

- юніт: backoff, dedupe_key, вибір обробника, `skipped` при зміні стану;
- інтеграційні (тестова база): `transition_with_outbox` атомарність (ROLLBACK
  не лишає рядка), sweeper виконує й не дублює, 8 невдач → `failed` + один алерт;
- архітектурний: у `app/api` заборонено прямі `setPromTTN/setRozetka*/setEpicentr*`
  поза `lib/outbox/handlers` (після фази 2).

## 10. Питання власнику (потрібно вирішити до фази 1)

1. **Робимо взагалі?** Альтернатива — лишити крони-самолікування і додати лише
   повтори для уведомлень покупцю (маленька правка). Outbox варто робити, якщо
   важливі слід у картці замовлення й тиша в Telegram під час повторів.
2. **Vercel Queues (фаза 3)** — брати бету чи обійтись sweeper раз на хвилину?
   Моя рекомендація: спочатку без Queues; додати, якщо хвилина затримки пушу
   заважає (для Rozetka SLA «88 год» — не заважає).
3. **Уведомлення покупцю** через outbox — зараз Telegram є, email є, SMS/Viber
   без провайдера. Включаємо email+Telegram у фазу 2?
4. **Поріг алерту**: 8 спроб / ~доба — ок, чи хочете раніше (наприклад, 1 год)?
