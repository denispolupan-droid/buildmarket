Цель: полноценный управленческий учёт уровня 1С/BAS (товары, взаиморасчёты,
продажи, возвраты, отчёты). Аудит: 4 параллельных исследования кода + проверка
живых данных прода (оборотка, инварианты).

## 1. Вердикт

Фундамент **сильный и правильный** — это не «магазин с Excel», а настоящее
учётное ядро: двойная запись, FIFO-партии, документы со сторно, автоинварианты.
Проблема не в архитектуре, а в **дырявых потоках**: часть хозяйственных операций
не доезжает до леджера, из-за чего P&L и взаиморасчёты врут.

Проверка прода: все 6 инвариантов OK, но оборотка показывает **выручку 1 180 грн
при себестоимости 5 218 грн** — выручка систематически теряется (см. K1).

## 2. Что уже есть и работает (фундамент)

- **Двойная запись**: `money_entries` append-only, пары проводок с общим txn_id
  через RPC `record_money_txn`, идемпотентность по ключу, guard-триггеры от
  UPDATE/DELETE. Баланс Σ=0 по построению.
- **Документы**: `acc_documents`/`acc_document_lines`, draft→confirmed→cancelled,
  сторно вместо редактирования, годовая нумерация (`РН-2026-0001`), цепочки
  PO→приход→возврат, корректировки PO.
- **Себестоимость**: FIFO-партии (`stock_batches`, FOR UPDATE SKIP LOCKED),
  landed costs с распределением на партии, переоценка avg_cost из партий.
- **Склад**: append-only `stock_movements`, материализованный `stock_balance`
  с CHECK-констрейнтами (не уходит в минус), атомарные резервы с TTL.
- **Контроль**: `check_invariants()` — 6 инвариантов (остатки=движения, Σ=0,
  кэш=леджер, резервы, оверсейл, FIFO≥0) + ежедневный крон с Telegram-алертом.
- **Взаиморасчёты**: AR (договоры, aging, акт сверки, банковский импорт Mono),
  AP (payables из леджера + фиксация оплат), баланс маркетплейсов с ручной
  сверкой, касса (ПКО/РКО), партнёрский баланс дропшиперов (отдельный реестр).
- **Возврат поставщику**: полный флоу UI+API+леджер.
- **Безопасность**: RLS deny-all на учётных таблицах, SECURITY DEFINER
  закрыты от анонимного RPC, доступ только через service role.

## 3. Критические дыры (P0 — из-за них учёт врёт)

**K1. Выручка не записывается для заказов без customer_id.**
`lib/accounting/documents.ts:268`: `if (doc.customer_id && totalAmount > 0)
recordShipment(...)`. Маркетплейс-заказы и гостевые заказы сайта не имеют
customer_id → их продажа попадает в COGS и долг поставщику, но НЕ в выручку.
Факт на проде: revenue 1 180 грн при 7 подтверждённых продажах.
→ P&L занижен на большую часть оборота.

**K2. Комиссии маркетплейсов и COD-начисления партнёрам пропускаются при
авто-доставке.** `recordMarketplaceCommission` и `credit_cod_to_partner`
вызываются только в ручном PATCH-обработчике заказа. Крон
`sync-delivery-status` ставит `delivered` напрямую в БД, минуя эти хуки →
для заказов, чью доставку определил крон, комиссия и COD не записываются.

**K3. Поступления наложенного платежа (НП) не попадают в леджер вообще.**
Когда Нова Пошта выплачивает COD по собственным/маркетплейс-заказам, никто
не пишет DR bank / CR customer. Дебиторка не закрывается, денежный поток
неполный. Импорта реестров выплат НП нет (банковский импорт парсит только
Monobank и только входящие B2B).

**K4. Клиентский возврат — сломанная семантика, флоу нет.**
`return_out` в TS списывает склад, но проводит `recordReturn` (сторно выручки
клиента — логика клиентского возврата); `return_in` приходует товар, но не
пишет ни одной денежной проводки; в сиде БД подписи противоположны
(`return_out` = «повернення постачальнику»). Целостного флоу
«restock + сторно выручки + возврат денег» не существует; UI подписывает
типы по-разному на разных экранах.

## 4. Высокие риски (P1 — целостность ядра)

- **FIFO молча недосписывает**: `consume_stock_fifo` при нехватке партий не
  бросает ошибку, а возвращает стоимость фактически списанного → тихое
  занижение COGS и минусовые движения (комментарий в documents.ts:157 обещает
  обратное).
- **Неатомарность проведения**: `confirmDocument` = серия отдельных await
  (движения → апдейт документа → 1-2 проводки). Падение посередине оставляет
  полупроведённый документ. Идемпотентность и инварианты страхуют, но
  консистентность в моменте не гарантирована.
- **Dropship-проводки вне документа**: COGS+долг поставщику пишутся отдельно
  от confirmDocument → cancelDocument их не видит; нужен парный
  reverseDropshipLedgerExtras (уже ловили висящий долг по #26071005).
- **Race повторной отгрузки**: в /ship между SELECT существующей РН и созданием
  новой нет блокировки — параллельные клики могут создать два sale-документа.
- **supplier_return без контроля количества**: можно вернуть поставщику больше,
  чем пришло (комментарий «P5» помечает проверку как нереализованную).
- **Кредитный лимит не проверяется при отгрузке**: `checkCreditAvailability`
  написан, но не вызывается ни в ship, ни в confirm.

## 5. Средние (P2 — полнота и UX)

- Дашборд финансов считает выручку/маржу из `orders` + `product_stock`, а
  «Звіти» (P&L) — из подтверждённых `acc_documents`: два источника правды,
  числа расходятся. Комиссия на дашборде аппроксимируется клиентски.
- Возвраты/отмены на Rozetka/Prom после создания заказа не обрабатываются
  (синк тянет только «в обработке»); комиссия при возврате не восстанавливается.
- Возврат денег клиенту не привязан к возврату товара (есть только отмена
  ошибочного платежа).
- Нет UI ручного добавления операционного расхода.
- Дублированный код банковского импорта (страница + дровер), только входящие,
  только Monobank.
- Ваучер оплаты поставщику не имеет страницы (ссылка-заглушка в payables).
- Мёртвый/битый запрос в stock/reorder (page.tsx:13-20).
- `lib/accounting/supplier-order.ts` — нерабочий скелет (пустые шаблоны Excel).

## 6. Чего нет из «классической 1С/BAS» (архитектурные достройки)

| Механизм | Статус | Нужен ли |
|---|---|---|
| Закрытие периодов (запрет проводок задним числом) | нет | ДА — обязательный для доверия к отчётам |
| Инвентаризация (план/факт/ведомость расхождений) | только doc_type-заглушка | ДА — без неё склад разъедется с реальностью |
| Возвраты как первокласс-документы со ссылкой на реализацию | нет | ДА (см. K4) |
| AP-aging (старение кредиторки) | нет (есть только AR) | Желательно |

| План счетов как справочник с иерархией | enum-строки | НЕ нужен на этом масштабе — enum достаточно |
| Курсовые разницы / мультивалюта | заготовки | Не нужно (грн) |
| НДС / налоговые накладные | нет | Не нужно (ФОП без НДС), вернуться при смене статуса |

## 7. План внедрения (рекомендация)

### Этап 1 — «Правдивый P&L» (первым, всё остальное без него бессмысленно)
1. **Выручка для всех продаж**: убрать условие customer_id; дебет-сторона по
   каналу: клиент → `customer`; маркетплейс → `customer` c counterparty
   `mp:rozetka`/`mp:prom` (дебиторка маркетплейса); COD-гость → новый счёт
   `cod_transit` (деньги в пути у НП).
2. **Единый пост-хук delivered**: вынести комиссию + COD-начисление в функцию
   `applyDeliveredEffects(orderId)` и вызывать из PATCH И из крона
   sync-delivery-status (идемпотентно — ключи уже есть).
3. **Импорт реестра выплат НП**: второй парсер в банковском импорте
   (CSV реестра НП) → DR bank / CR cod_transit(или customer), комиссия НП → расход.
4. **Дашборд на леджер**: те же источники, что у «Звітів», либо явная пометка
   «оперативная оценка» + ссылка на точный P&L.
5. Бэкфилл: разово дозаписать выручку по уже отгруженным заказам
   (idempotency-ключи защищают от дублей).

### Этап 2 — Возвраты
6. Зафиксировать семантику: `return_in` = возврат ОТ клиента (приход товара
   новой FIFO-партией + DR revenue / CR customer + сторно COGS), `return_out` =
   возврат ПОСТАВЩИКУ (синоним supplier_return — свести к одному типу).
   Выровнять подписи во всех экранах.
7. Флоу «Оформити повернення» из карточки заказа: выбор позиций (частичный),
   для own-строк — restock, для dropship — сторно COGS и долга поставщику;
   опционально «повернути кошти» (DR customer / CR bank|cash).
8. Маркетплейс-возвраты: тянуть статусы returned/declined из Rozetka/Prom
   после создания заказа, авто-создавать возврат + восстанавливать комиссию.

### Этап 3 — Целостность ядра
9. `consume_stock_fifo`: RAISE EXCEPTION при нехватке (политика «запрет
   отрицательного склада» уже задана констрейнтами — довести до FIFO).
10. Атомарность: перенести проведение документа в одну SQL-функцию
    (confirm в одной транзакции: движения + партии + проводки), либо
    компенсационный runner + пост-чек инвариантов на каждый confirm.
11. Dropship-проводки — внутрь confirmDocument (одна точка входа/сторно).
12. Advisory-lock на отгрузку по order_id (анти-double-ship).
13. Контроль qty в supplier_return; вызов checkCreditAvailability при
    отгрузке в кредит.

### Этап 4 — 1С-достройки
14. **Закрытие периода**: таблица `acc_periods` + триггер запрета
    insert в закрытый месяц (movements + money_entries) + UI «Закрыть месяц»
    с прогоном инвариантов перед закрытием.
15. **Инвентаризация**: документ (снимок план-остатков → ввод факта →
    авто-списание/оприходование расхождений отдельными строками + ведомость).
16. **Отчёты**: оборотно-сальдовая ведомость (счёт × контрагент × период),
    товарный отчёт по SKU (приход/расход/остаток/маржа), AP-aging.
17. Мелочи из P2 (UI расхода, страница ваучера, объединение банк-парсеров,
    чистка мёртвого кода).

## 8. Принципы (зафиксировать как правила проекта)

- Единственный источник денежной правды — `money_entries`; UI не считает
  деньги из `orders`.
- Каждая хозяйственная операция = документ + проводки в ОДНОЙ точке кода;
  статусные хуки (delivered и т.п.) — общие функции для ручного и кронового пути.
- Проведённые документы не редактируются — только сторно/корректировка.
- Любая новая денежная ветка обязана иметь idempotency-ключ и попадать под
  существующие инварианты (при необходимости — добавить новый инвариант).
