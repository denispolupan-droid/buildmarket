## Що пропонується (три етапи, кожен цінний окремо)

### Етап 1. Дизайн-токени (≈4–6 робочих днів)

Мета: жоден новий колір у `app/admin` не пишеться hex-ом; темна тема перестає розходитись.

1. Розширити токени на `:root`: семантичні (`--surface`, `--surface-2`, `--line`, `--ink`,
   `--ink-2`, `--ink-3`, `--ok`, `--warn`, `--danger`, `--info` + їхні `*-bg`), відступи
   (`--sp-1…--sp-8`), радіуси, тіні. Темна тема — лише перевизначення на `[data-theme="dark"]`.
2. Кодмод по `app/admin`: топ-20 hex-значень (покривають ≈70 % вживань) → `var(--…)`.
   Робиться скриптом з таблицею відповідностей, перевіряється `git diff` + Playwright-скріншоти
   трьох екранів до/після (журнал, картка, фінанси) у світлій і темній темі.
3. Архітектурний тест: нові hex у `app/admin/**/*.tsx` — порушення (allow-list для SVG/брендів).
4. Inline `style={{` **не чіпаємо масово** — лише кольори всередині них. Переписувати
   6 964 рядки на класи зараз не окупається; правило: нові компоненти — класи `fin-*`, старі
   правляться по дорозі.

Ризик: низький (чисто візуальний); відкат — один коміт. Що може піти не так: кодмод
замінить hex у рядку, який не колір (ID, хеш) — тому allow-list і перегляд diff по файлах.

### Етап 2. Спільний шар даних (≈6–8 днів, по екранах)

Мета: один спосіб читати дані в адмінці — кеш, повтор, стан завантаження/помилки, оновлення
після мутації; прибрати 56 копій `useEffect + fetch`.

1. Підключити SWR (менший за React Query, без провайдера, достатньо для адмінки) і написати
   `lib/admin/api.ts`: типізований `adminFetch` з обробкою `rid`/помилок `withApi`, плюс
   `useAdminQuery(key)` / `useAdminMutation()` поверх SWR. Одне місце для toast про помилку.
2. Переводити по екрану, починаючи з найбільшого виграшу й найменшого ризику: Фінанси
   (вкладки з однаковою формою «період → дані»), Закупівля, Контрагенти, Ціни. Журнал
   замовлень (`useAdminOrders.ts`, 2 138 рядків) — **останнім і окремим рішенням**: він
   працює, його правлять найчастіше, і він потребує не SWR, а розбиття на 5–6 хуків.
3. Після кожного екрана — e2e-спек на маршрут (зараз адмінка майже без них), це й стане
   регресійною сіткою для наступних етапів.

Ризик: середній — зміна поведінки завантаження (що показується під час повтору, коли
оновлюється список після дії). Пом'якшення: екран за екраном, кожен з e2e, деплой по одному.

### Етап 3. Доступність і модалки (≈2 дні)

1. Чотири `*DraftManager.tsx` перевести на спільний `Modal`/`<dialog>` або на `popover`
   (вони не блокують сторінку — панель чернеток ближче до popover).
2. `Modal`: додати `aria-labelledby` з `title`, початковий фокус на перший елемент форми,
   повернення фокусу на кнопку-відкривач при закритті.
3. Таблиці: `scope="col"`, сортування з `aria-sort`; іконки-кнопки без тексту — `aria-label`
   (зараз 85 на 699 файлів). Шорткати: `/` — пошук, `n` — нове замовлення, `Esc` — закрити.

Ризик: низький.

## Що свідомо НЕ пропонується

- **Tailwind.** Встановлений, але не підключений і не використовується; підключення дало б
  другу систему стилів поруч із `fin-*`. Рішення: видалити з залежностей або лишити як є,
  але не починати.
- **Переписування великих екранів** (PricesClient, NewOrderModal, ProcurementDetail) заради
  розміру. Розбивати лише там, де це потрібно для етапу 2.
- **Редизайн.** Стиль `fin-*` — прийняте рішення власника; план про інженерну основу, не про вигляд.
- **Окремий планшетний макет.** Спершу токени й шар даних; планшет — коли буде запит.

## Порядок і перевірка

Етап 1 → етап 3 → етап 2 (найризикованіший — останнім, уже з токенами й e2e). Кожен етап
окремою гілкою, деплой по явній команді, перед деплоєм — скріншоти до/після і e2e. Сумарно
≈12–16 робочих днів фоном, без зупинки поточних задач.
