## Що пропонується (три етапи, кожен цінний окремо)

### Етап 1. Дизайн-токени (≈4–6 робочих днів) — крок 1 зроблено 08.11.2026

Зроблено: 36 нових токенів на `:root` + темні значення (`app/globals.css`), кодмод замінив
1 508 hex у 128 файлах `app/admin` на `var(--…)` (топ-45 значень; світлі значення токенів =
рівно ті hex, що були, тому 8 екранів у світлій темі збіглися до пікселя зі знімками «до»);
храповик `tests/admin-color-tokens.test.ts` + `tests/admin-color-tokens.baseline.json`
(лишилось 613 hex у 100 файлах — кількість у файлі може лише зменшуватись, новий файл — 0;
після зменшення перебудувати baseline: `node scripts/admin-color-baseline.mjs`).
Свідомо не чіпали: JSX-атрибути (`color="#…"` іконок lucide, ~130), файли, що генерують
окремий HTML для друку/вікон (`dispatch/DispatchClient`, `prices/PricesClient`,
`products/import/ImportClient`, `suppliers/unmapped/UnmappedClient`) — там `var()` не має
`:root`, і рідкісні відтінки поза топ-45. Це — крок 2 етапу, по дорозі.

Мета: жоден новий колір у `app/admin` не пишеться hex-ом; темна тема перестає розходитись.

1. Розширити токени на `:root`: семантичні (`--surface`, `--surface-2`, `--line`, `--ink`,
   `--ink-2`, `--ink-3`, `--ok`, `--warn`, `--danger`, `--info` + їхні `*-bg`), відступи
   (`--sp-1…--sp-8`), радіуси, тіні. Темна тема — лише перевизначення на `[data-theme="dark"]`.
2. Кодмод по `app/admin`: топ-20 hex-значень (покривають ≈70 % вживань) → `var(--…)`.
   Робиться скриптом з таблицею відповідностей, перевіряється `git diff` + Playwright-скріншоти
   трьох екранів до/після (журнал, картка, фінанси) у світлій і темній темі.
3. Архітектурний тест: нові hex у `app/admin/**/*.tsx` — порушення (allow-list для SVG/брендів).
4. Inline `style={{` **не чіпаємо масово** — лише кольори всередині них. Переписувати
   6 964 рядки на класи зараз не окупається; правило: нові компоненти — класи `fin-*`, старі
   правляться по дорозі.

Ризик: низький (чисто візуальний); відкат — один коміт. Що може піти не так: кодмод
замінить hex у рядку, який не колір (ID, хеш) — тому allow-list і перегляд diff по файлах.

### Етап 2. Спільний шар даних (≈6–8 днів, по екранах) — розпочато 08.11.2026

Зроблено: SWR 2.5.1, `lib/admin/api.ts` (`adminFetcher`, `AdminApiError` з `rid`, `useAdminQuery`;
без автооновлення на фокусі й автоповторів — як було в `useEffect`). Переведено три екрани
Фінансів, що читали дані в ефекті: закриття періодів, повернення, коригування боргу (e2e
`tests/e2e/admin/finance-data-layer.spec.ts`). Решта екранів Фінансів серверні, їхні `fetch` —
дії (POST) або пошук за вводом. `useAdminMutation` не робимо, доки не буде кількох однакових
мутацій. Далі переведено Закупівлю (відправники, інвентаризація, шухляда ЗП), Контрагентів
(договори, транзакції, історія) і Ціни (журнал, акції МП); e2e `data-layer-screens.spec.ts`.

Свідомо лишились на `fetch`: борги в `SupplierPayForm` (рознесення оплати лише зі свіжих
даних, без показу з кешу), файл рахунку ЗП (підписаний URL із терміном дії), попередній
перегляд цін і PDF.

Рішення власника 08.11: довести до кінця. Переведено й решту розділів (SEO, блог, відгуки,
Rozetka, модель цін, вітрина, налаштування, чати, пошта, постачальники, частина модалок) і
довідники журналу замовлень (постачальники, відправники). Дим усіх екранів:
`tests/e2e/admin/all-screens-smoke.spec.ts`.

Лишаються на `fetch` навмисно: пошук із затримкою під час вводу; форми, які заповнюються
завантаженими даними й потім редагуються (накладні `CreateTTNModal`, `RzDeliveryTtnModal`,
`RozetkaDeliveryTtnModal`, `ProductForm`, клієнт у `NewOrderModal`); ланцюгові завантаження
(`RegisterPanel`, `DispatchClient`, листи в `MailClient`, реєстри й історія клієнта в журналі).
Розбиття `useAdminOrders.ts` (2 138 рядків) на менші хуки — окрема робота, в цей етап не входить.

Мета: один спосіб читати дані в адмінці — кеш, повтор, стан завантаження/помилки, оновлення
після мутації; прибрати 56 копій `useEffect + fetch`.

1. Підключити SWR (менший за React Query, без провайдера, достатньо для адмінки) і написати
   `lib/admin/api.ts`: типізований `adminFetch` з обробкою `rid`/помилок `withApi`, плюс
   `useAdminQuery(key)` / `useAdminMutation()` поверх SWR. Одне місце для toast про помилку.
2. Переводити по екрану, починаючи з найбільшого виграшу й найменшого ризику: Фінанси
   (вкладки з однаковою формою «період → дані»), Закупівля, Контрагенти, Ціни. Журнал
   замовлень (`useAdminOrders.ts`, 2 138 рядків) — **останнім і окремим рішенням**: він
   працює, його правлять найчастіше, і він потребує не SWR, а розбиття на 5–6 хуків.
3. Після кожного екрана — e2e-спек на маршрут (зараз адмінка майже без них), це й стане
   регресійною сіткою для наступних етапів.

Ризик: середній — зміна поведінки завантаження (що показується під час повтору, коли
оновлюється список після дії). Пом'якшення: екран за екраном, кожен з e2e, деплой по одному.

### Етап 3. Доступність і модалки (≈2 дні) — крок 1 зроблено 08.11.2026

Зроблено: чотири документні панелі (нове замовлення, ЗП, прихід, складський документ) —
`role="dialog"`, `aria-modal="false"`, `aria-label`, спільний хук `useDocPanel`
(`app/components/admin/ui/useDocPanel.ts`): фокус на перше поле при відкритті, Escape
згортає панель (форма не губиться; випадні списки, що самі обробили Escape, не зачіпає),
повернення фокусу туди, звідки відкрили. Панелі свідомо НЕ переведені на `<dialog>.showModal()`:
вони не модальні — сторінка й вкладки чернеток під ними мають працювати. Спільна `Modal`:
`aria-labelledby` із заголовка, фокус на перше поле вмісту (а не на хрестик, як робить
`showModal()` сам). `<th scope="col">` у всіх 245 заголовках таблиць адмінки. Перевірено
Playwright на тестовій базі: панель — фокус в INPUT, Escape → 0 діалогів / 1 вкладка; модалка
«Новий контрагент» — фокус на першому полі. Tailwind видалено (рішення власника 08.11):
пакети `tailwindcss`, `@tailwindcss/postcss` і `postcss.config.mjs` (підключення
`@import "tailwindcss"` ніколи не було, CSS не змінився — 8 екранів збіглися до пікселя).
Лишилось на крок 2: `aria-label` для іконок-кнопок з лише `title`, `aria-sort` на сортованих
колонках, шорткати (`/` пошук, `n` нове замовлення).

**Темна тема в адмінці (08.11.2026, рішення власника):** перемикач у підвалі сайдбара
(`data-admin-theme-toggle`), ключ `localStorage.admin_theme`, діє лише на `/admin/*`
(`lib/theme.tsx` + blocking-скрипт у `app/layout.tsx` до першого кадру); сайт лишається
світлим завжди (історія з вебв'ю месенджерів). У темній темі `.admin-layout` отримує темні
`--border/--border-light/--text-muted` (інакше світлі межі адмінки перекривали б тему).

1. Чотири `*DraftManager.tsx` перевести на спільний `Modal`/`<dialog>` або на `popover`
   (вони не блокують сторінку — панель чернеток ближче до popover).
2. `Modal`: додати `aria-labelledby` з `title`, початковий фокус на перший елемент форми,
   повернення фокусу на кнопку-відкривач при закритті.
3. Таблиці: `scope="col"`, сортування з `aria-sort`; іконки-кнопки без тексту — `aria-label`
   (зараз 85 на 699 файлів). Шорткати: `/` — пошук, `n` — нове замовлення, `Esc` — закрити.

Ризик: низький.

## Що свідомо НЕ пропонується

- **Tailwind.** Був у залежностях, але не підключений і не використовувався; підключення дало б
  другу систему стилів поруч із `fin-*`. Видалено 08.11.2026 за рішенням власника.
- **Переписування великих екранів** (PricesClient, NewOrderModal, ProcurementDetail) заради
  розміру. Розбивати лише там, де це потрібно для етапу 2.
- **Редизайн.** Стиль `fin-*` — прийняте рішення власника; план про інженерну основу, не про вигляд.
- **Окремий планшетний макет.** Спершу токени й шар даних; планшет — коли буде запит.
